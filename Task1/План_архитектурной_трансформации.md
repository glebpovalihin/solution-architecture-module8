# План архитектурной трансформации ИТ-ландшафта Fast Cargo

## 1. Выгоды бизнеса

- Десятикратный рост объемов при интеграции ИТ-систем с холдингом "Продукты с душой"
- Масштабируемость x10: платформа принимает до 500 тыс отправлений в сутки без переписывания заново
- Доступность 99.95%: исключаются простои приема заказов из-за тяжелых финансовых отчетов и пиков сезона
- Нулевые потери платежных вебхуков банка (0% таймаутов): каждая потерянная оплата - прямой убыток.
- Соответствие ФЗ-152 и PCI DSS: снижение регуляторных и штрафных рисков при работе с персональными и платежными данными
- Аналитика в DWH холдинга с задержкой не более 5 секунд: операционные решения принимаются по актуальным данным, а не по устаревшим

## 2. Базовая и целевая архитектура

### AS-IS

Трехслойный ландшафт:
- фронт-офис (личный кабинет, мобильное приложение, эквайринг)
-  самописный middleware-шлюз на Python (FastAPI/Uvicorn),
- бэк-офис в виде монолита BFF с модулями Заказы, Warehouse, Доставка, Финансы
- Хранение - единый физический инстанс PostgreSQL с тремя схемами: integration, master_data, operational.

Главный антипаттерн: общая база данных как единая точка отказа.
Модули связаны жесткими связями между таблицами, тяжелые отчеты модуля Финансы блокируют транзакционные записи и парализуют регистрацию заказов.
Дополнительно - единый BFF-слой, изменения веба ломают API мобильного приложения, падение шлюза по таймауту 504 с потерей банковских вебхуков, долгий релизный цикл монолита

### TO-BE

Событийно-ориентированная микросервисная архитектура с разделением по принципу Database-per-Service.
Домены: заказы, склад, доставка, финансы, профили клиентов, платежи.

Ключевые паттерны взаимодействия :
- ПДн - выделенный микросервис профилей с отдельной базой, внешние системы получают данные только в обезличенном виде через сурогатные UUID
- Платежи изолированы в отдельный модуль, PAN не попадает в контур Fast Cargo
- Аналитика вынесена в выделенный контур CDC, доставка в DWH с задержкой менее 5 секунд
- EDI реализует асинхронную обработку цепочки ORDERS -> DESADV -> INVOIC через брокер Kafka с паттерном Outbox, итоговая согласованность без распределенных блокировок и меж доменных JOIN
- IoT и телематика - поток координат направлен в Kafka, а не в транзакционную СУБД, деградация склада или биллинга не влияет на прием геоданных

## 3. Область применения

### In-scope

- Монолит бек офиса: декомпозиция на доменные микросервисы модулей Заказы, Warehouse, Доставка, Финансы
- Middleware-шлюз FastAPI: замена на API Gateway, очереди для вебхуков
- Схема PostgreSQL - разделение на независимые базы по доменам
- Фронт-офис - выделение отдельных BFF для личного кабинета и мобильного приложения
- Новые компоненты (EDI шлюз, платформа телематики, интеграция с CRM холдинга, изолированный платежный модуль, контур аналитики)

### Out-of-scope

- Внутренние системы холдинга "Продукты с душой"- работаем с текущими интеграционными контрактами, их код и инфраструктура не меняются
- Банк эквайер и его инфраструктура - внешний провайдер, интеграция только по сценарию редиректа или виджета
- Внешние подрядчики Fast Cargo  и облачные сервисы автоматизации работают как есть
- Справочники master_data только читаются и не трансформируются

## 4. Ограничения и допущения

Ограничения:

- Сроки: 3 месяца - аналитика в реальном времени в DWH холдинга, 12 месяцев - полный демонтаж монолита и переход на микросервисы
- Первые 3 месяца: запрещено изменение исходного кода легаси монолита и создание SQL нагрузки на операционную базу
- Целевая архитектура - запрет распределенных блокировок СУБД и меж доменных JOIN, итоговая согласованность через события
- Комплаенс - ФЗ-152, PCI DSS требуют изоляции платежного контура и контура персональных данных
- Инфраструктура переходного периода - до 2х кратоного роста текущих мощностей на время параллельной работы старого и нового контуров

Допущения:

- Холдинг предоставляет контракты EDI (форматы ORDERS/DESADV/INVOIC) и доступ к DWH
- Банк эквайер поддерживает редирект или виджет без передачи PAN в контур Fast Cargo
- Бюджет согласуется с рисковым буфером 20-30% на невыявленные интеграционные сложности

## 5. Transition Architecture (тактический план на 3 месяца)

| Уровень архитектуры | Текущее состояние (AS-IS) | Переходное состояние (через три месяца) | Обнаруженный разрыв (GAP) и локация изменений |
|---|---|---|---|
|  Данные (Data) | Аналитические SELECT запросы идут напрямую в операционную базу PostgreSQL, ежемесячные отчеты блокируют транзакционные записи | Аналитические данные вычитываются асинхронно из WAL-логов без нагрузки на транзакционные таблицы, статусы заказов доходят до DWH холдинга за секунды за счет CDC | Разрыв заключается в отсутствии выделенного контура аналитики. Локация изменений - слой хранения: развертывание CDC-коннектора (Debezium/Kafka Connect), чтение с реплики, топики Kafka |
| Приложения (Apps) | Шлюз FastAPI расходует воркеры на ожидание бэкенда, падает по таймауту 504 и теряет вебхуки банка; монолит сильносвязан, изменения любого модуля требуют деплоя всего кода | Легаси-код не меняется, добавлены новые компоненты вне монолита: CDC-коннекторы с обезличиванием ПДн на стороне продюсера, консьюмеры на стороне DWH. Трафик фронта не затрагивается | Разрыв - отсутствует асинхронный канал выгрузки данных без участия кода монолита. Локация это прикладной слой - развертывание Debezium/Kafka Connect и консьюмеров вне монолита |
| Инфраструктура (Infra) | Единый физический инстанс PostgreSQL в локальном ЦОД, утилизация на пределе из за тяжелых отчетов и пиков | Выделен Kafka кластер и ресурсы отдельно от боевого контура, чтение WAL с реплики, защищенный сетевой канал до DWH холдинга, мониторинг лага репликации | Разрыв - нет защищенного канала в холдинг. Локация - инфраструктурный слой: резервирование ресурсов, реплика, сетевой туннель |

## 6. Переходное состояние: аналитика в реальном времени

Паттерн: CDC с брокером Kafka
Поток данных: WAL-лог PostgreSQL реплики -> Debezium/Kafka Connect (обезличивание ПДн на продюсере) -> топики Kafka по доменам -> консьюмер на стороне DWH холдинга -> DWH

Обоснование решения:
- CDC читает журнал репликации WAL - SQL нагрузка на операционную базу отсутствует, блокировок нет, жесткое ограничение соблюдено
- Исходный код легаси монолита не изменяется - коннектор работает на уровне СУБД, деплой монолита не требуется
- Задержка доставки - доли секунды плюс транспорт, что укладывается в требование менее 5 секунд
- Kafka буферизует события что предотвращает потерю данных.
- Чтение выполняется с реплики, а не с мастер инстанса - нулевое влияние на производительность операционного контура
- Обезличивание выполняется на продюсере до публикации в топики: паспорта, телефоны и email заменяются на суррогатные UUID. В Kafka и DWH попадают только обезличенные данные, выполняется требование ФЗ-152 соблюдено

## 7. Дорожная карта, риски и план перехода

### Пакеты работ и сроки

- Инфраструктура потока данных (срок реализации в недели 1-4): Kafka-кластер, реплика PostgreSQL, сетевой канал до DWH холдинга, мониторинг лага. Ответственные: инженер эксплуатации Fast Cargo, инфраструктура холдинга
-  CDC коннекторы (срок  реализации в недели 2-6): коннекторы Debezium (orders, order_items, warehouse_stocks, waybills, invoices), обезличивание ПДн, топики по доменам, политики хранения
- Потребители в DWH (недели 3-8): консьюмеры со стороны холдинга, сверка данных с операционной базой
- Пилот и ввод в эксплуатацию (недели 6-12): нагрузочные тесты на пиковом трафике, теневой прогон, официальный ввод потока в промышленную эксплуатацию

### Управление рисками и план отката

Риски:
- Отставание репликации при пиках - мониторинг Kafka consumer lag, алерт при накоплении лага
- Влияние на операционную БД - чтение только с реплики, лимиты на число коннекторов
- Потеря событий при падении DWH - retention в Kafka покрывает время простоя
- Утечка ПДн - обезличивание на продюсере до публикации в Kafka, аудит канала

План отката:

1. Остановка CDC коннекторов - операционная БД возвращается к штатному режиму без влияния
2. Остановка консьюмеров DWH - события остаются в Kafka, потери нет
3. Проверка метрик операционной базы (блокировки, утилизация) - подтверждение стабильности.
4. Возврат к исходному состоянию: DWH холдинга перестает получать поток до устранения проблемы, операционный контур работает штатно. Деплои не требуются - код монолита не изменялся, откат заключается в отключении новых компонентов

### Критерии успешности и переключение

Критерии:

- Задержка доставки статусов заказов в DWH не более 5 секунд (p95)
- Отсутствие SELECT запросов аналитики к операционной базе
- Отсутствие изменений исходного кода легаси-монолита
- Расхождение данных при сверке не более 0.1%

Переключение:
1. Теневой прогон 2 недели - конвейер CDC работает и пишет в DWH холдинга, данные не используются потребителями
2. Сверка данных конвейера с операционной базой по контрольным сущностям через реплику
3. Ввод в промышленную эксплуатацию - поток становится источником данных для DWH холдинга, наблюдение 1 неделя
4. Подключение потребителей холдинга (дашборды, отчеты) к потоку реального времени
